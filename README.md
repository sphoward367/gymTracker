LiftLog: Development Reflection

LiftLog is an offline-first gym workout tracker built as a PWA, developed both as a portfolio piece and a functional product for personal use. The project was planned and built using AI-assisted development throughout, with Claude handling research synthesis, documentation generation, and code production while I retained ownership of all architecture and product decisions.

Technical Design

The architecture was designed around a strict service layer pattern where components never access Firestore directly, with all data flowing through typed service modules. This separation proved critical when the project pivoted from React Native to a PWA before development began. The entire service layer, data model, and TypeScript interfaces carried over unchanged, with only the UI layer requiring a rethink.
Several design decisions were made to support long-term flexibility. An exercise data normalisation layer abstracts the underlying source behind a single interface, meaning the bundled 800-exercise JSON dataset can be swapped to an 11,000-exercise hosted API by modifying two lines. The Firestore data model uses strategic denormalisation, storing exercise names directly in workout documents, to eliminate joins, protect historical records across data source changes, and enable constant-time PR lookups. Offline capability combines Firestore IndexedDB persistence, Service Worker static asset caching, and localStorage draft recovery, allowing the app to function identically without a network connection. A clock-diff timer pattern was implemented to work around iOS Safari's suspension of background JavaScript, using absolute timestamps and recalculating elapsed time on visibility change rather than relying on continuous intervals.

AI Challenges and Solutions

Working with AI code generation surfaced three recurring problems. First, context loss. Over long sessions the AI would forget established conventions and architecture decisions. This was solved by creating modular configuration files (AGENTS.md, agent_docs/) loaded at the start of each session, effectively acting as external memory. Second, scope creep. The AI consistently introduced unrequested features and over-engineered solutions. This was controlled through explicit constraint rules, phase-gated task lists, and deliberately prompting for the simplest viable approach. Third, hallucinated APIs and architectural drift. The AI would generate deprecated syntax or gradually break established patterns across files. This was prevented by providing verified code examples and exact import patterns in the agent documentation, with strict TypeScript and pre-commit type checking catching violations automatically before they compounded.

The most effective takeaway was that AI-assisted development produces significantly better results when paired with strong upfront planning. The iterative four-phase approach of research, PRD, technical design, then agent configuration meant each phase acted as a quality gate for the next, and the AI always had well-defined boundaries to work within rather than open-ended freedom to improvise.
